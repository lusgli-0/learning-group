## 本周任务

请大家在这个 `README.md` 中写入自己的 GitHub 主页地址，例如：

- https://github.com/lusgli-0

然后提交一个 Pull Request（PR）请求合并。

PR 的含义就是：**“我改了内容，请你 review，确认后合并。”**

这是团队协作最核心的动作，也是之后会持续使用的流程。

## 标准操作流程

`Fork → Clone → 建分支 → 修改 → commit → push → 发 PR`

看起来步骤多，但这是一个完整闭环。按流程走一遍就会了；遇到问题可以直接问 AI。

PR 合并后，你自己的临时分支可以删除。

## 为什么要先做这件事

当 README 里有了大家的主页地址，我们就能互相串门看代码，交流会更高效。

## 从现在开始的三条流程

### 一、个人代码放个人仓库

个人仓库可自行设置 public/private。

如果是公开代码并希望他人使用或修改，请补充：

- README.md（说明项目用途、运行方式等）
- License（明确授权方式）

这样做有两个好处：

1. 代码始终归你自己所有
2. 项目可展示、可复用，也可作为简历材料

### 二、主要通过 Issue 和 PR 协作

- **Issue**：提问、讨论、报 Bug
- **PR**：提交改动、发起评审

除 GitHub 外，也可以在群里、社区里交流，或直接私信沟通。

### 三、尽量每周一次分享会

暂定 3 人轮班：

- 每次由 1 人提前准备一个**最小可复现示例**并公开到仓库
- 现场讲解约 15 分钟

目的：建立线下连接、锻炼表达能力、通过讲清楚来加深理解。

## 后续会补充到仓库的内容

- 提交规范（commit message、分支命名）
- Review 指南（评论写法、Request changes / Approve 的使用）
- 其他实践中需要的协作说明

群里公告后续也会同步一份。

## 承诺与建议

只要大家把账号写进仓库文档里，我有时间就会去看代码，随机挑问题、随机修 Bug。修不动的会开 Issue，帮你把问题问清楚。

即使是 AI 生成的代码，只要功能靠谱，也会认真协助整理和重构。

最重要的还是自己动手写：看十遍不如敲一遍。

如果你目前没有代码基础，建议先跟教程手敲；相关新手材料后续也会逐步补充到仓库。
