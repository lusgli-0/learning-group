以下是这个部门的一些规定和流程：

## 一、信息同步机制

为了保持信息的公开透明与高效查询，我们制定了以下交流机制：

1. 信息中枢：我们几乎所有的信息和资源，都会统一发布在 **https://github.com/lusgli-0/learning-group**（就是你现在看到的这个仓库）。
2. 微信通知：凡仓库中涉及部门运行的内容发生更新，我们将通过微信群发布通知，简要说明更新的主要内容及对应文件位置，以便各位及时了解并快速定位相关新内容。
3. 公开透明：本仓库为 Public 状态，任何人都可以查看，欢迎大家监督和分享。
4. 互看代码：大家可以看到 README.md 里汇总了每位成员的 GitHub 账号。这份名单不仅是身份标识，更是大家互相交流的桥梁。你可以通过这份名单，去“串门”查看其他成员的开源代码、项目进度，互相学习、共同进步！

> 就像之前说的，几乎所有的信息和资源都会放在 learning-group，所以一定要看。

## 二、每周学习与分享机制

我们以每周为单元进行学习，分为**基础任务**和**扩展任务**。
- **基础任务**：保证基本节奏统一。
- **扩展任务**：了解各种框架、语言和技术，供学有余力的同学自主选择。我们一起学！

同时，我们希望一些练习题尽量贴近真实场景，而不是脱离实际的示例。因此会优先从社团内部需求、开源社区的真实问题和通用工程问题中取材，让成果逐步沉淀为可复用的积累。比如你今天写了一个小工具，下一个人做类似的东西时，可以**直接拿来用**，不用从零开始。

同时各位可以从现在开始自己写项目，比如我们现在可以用 GitHub Pages 写静态网站、用 JavaScript 写小工具、做点好看的特效和动效，或者折腾个小游戏。

> 我们用纯前端（HTML/CSS/JS），能做很多东西：
> - 所有"算出来给你看"的：计算器、换算器、二维码生成、成绩估算
> - 所有"处理本地文件"的：图片压缩、加水印、格式转换、Excel/CSV 解析
> - 所有"生成东西"的：随机点名、抽签分组、排班表、海报长图
> - 所有"展示类"：个人主页、班级相册、课表、倒计时
> - 所有"本地保存"的：笔记、待办（用浏览器存储，换设备不同步）
> 
> GitHub Pages 部署不限量。

### 周六固定分享 + 闲谈
- **时间**：每周六 18:00 - 20:00
- **议程**：
  - `18:00 - 18:30` 入场、吃零食（买点小零食、饼干、饮料，或者拼单点个披萨）、闲聊。同步一下这周遇到的新鲜事、踩过的坑，或者纯粹吐槽。谈论自己想做或正在做的项目，也可以趁这个时间拉别人“入伙”。
  - `18:30 - ` 正式分享。每次由三位同学轮班，一位同学至少讲 15 分钟。（暂定：个人报名+抽签）
  - **剩余时间**：自由交流与实操。不设固定议程，针对刚才分享的内容随意提问。这一周卡住的问题可以当面问，写的代码、提交的 Pull Request 也可以拿出来一起看，最近在做什么、对某个方向怎么看，甚至可以聊聊自己的专业课和作业。

### 分享讲什么？
这周你学到的一个东西。内容不设门槛——一个 bug 的成因、一个 API 用法、一个 shell 命令、一个软件功能，甚至书里的一句话，都算。关键不是讲得多牛，是"我这周确实碰过它"。

> 最好讲扩展任务的内容。
> 如果因为时间原因没有学代码，讲专业课内容也完全OK！

**分享规则**：
- 建议保留精髓文字（格式不限），代码建议提前写好最小可复现例子。
- 如果有整理，传到 `learning-group` 仓库指定位置，方便没来的同学复习。
- **“讲不出东西”是允许的**：这周没学到什么，就说踩了什么坑，卡在哪。
- **不搞形式主义**：不用 PPT（想用就用）、不评分、不签到、不考核。

> 安排轮班不是为了凑人数，而是让每个人都有开口的机会，让交流真正发生。

为什么开这个会：一是建立线下关系，二是锻炼表达能力（我自己也算一个），三是把一件事讲清楚，讲的过程本身就是加深理解。

## 三、成长路径（三个台阶）

为避免“只学不做”，我们将成长过程划分为三个阶段：

1. **第一级**：独立完成一个小功能的交付，走通从需求到上线的完整流程。
2. **第二级**：承接社团内部需求（如活动报名、现场签到、宣传页面等），这类需求明确、有真实用户、风险可控。
3. **第三级**：形成“内部需求 → 部门承接 → 沉淀为可复用工具”的良性循环，让部门的产出持续积累。

## 四、代码与协作规范

1. **个人代码**：放个人仓库，自己设置 public / private。公开的代码建议写 `README.md` 并选一个 license。这样代码始终是你自己的，还能向大家显摆——以后找工作、给人看作品，打开你自己的 GitHub 就有东西可看。
2. **文档沉淀**：所有流程、经验和常见问题，尽量沉淀到代码仓库文档中。
3. **交流渠道**：
   - **Issue**：用来提问、讨论、报 Bug。
   - **PR**：用来提交改动（“我改了东西，请你看一下，觉得行就合并进去”）。
   - 群里、社区里聊，或者直接给我发消息都可以。
4. **互相贡献**：通过仓库文档看其他朋友干了什么，挑点 Bug 发 Issue，或是帮忙扩展新功能。如果是纯 AI 写的代码，功能不错也可以帮忙整理和重构。
5. **基础规范**：提交规范（commit message、分支命名）和 Review 指南先由各仓库管理员负责。但最基础的变量名、写注释、拆文件等可读性规范是必须遵守的。

## 五、部门宗旨

部门最根本的目的是**促进同学之间的交流**。我们希望让编程与 AI 真正成为大家手里的工具，让大家在交流中互相了解、彼此启发。

同学们学业任务繁重，各项活动都以**自愿参与**为前提：
- 分享会能来就来，来不了说一声就行。
- 这周没有明显进展，说说遇到的困难同样受欢迎。

我们希望用宽松、真诚的氛围，让更多同学愿意留下来、愿意开口、愿意动手，让技术真正服务于大家的学习与成长。
